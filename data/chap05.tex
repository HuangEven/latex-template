\chapter{综合实验设计与结果分析}

\section{实验环境与软硬件配置}

同样是 百万级输入，检验能否找回异常交易，与测量一秒内能完成多少次查询，需要的记录并不相同。前者要对齐风险分数和标签；后者还要注明索引布局、批大小和计时边界。本章先列出共用的软硬件配置，再分别比较端到端检测、单卡交接和多卡扩展。

硬件环境方面，实验平台由多张同型号 GPU、主机 CPU、内存、SSD 以及对应 PCIe 拓扑组成。单卡实验使用 1 张 GPU 运行完整的候选召回与异常评分链路，主要观察第四章提出的数据路径优化、异步流组织、RAPIDS 后端重构、FAISS-GPU 前期接口验证经验和 FlashANNS 候选召回前端接入在单设备上的综合表现；多卡实验使用 2 张及以上 GPU，主要对应第五章中的索引复制（replicated）扩展、控制面调度、设备侧归并和 I/O 通道控制。由于本文后续还需要讨论拓扑差异对扩展结果的影响，GPU 型号、显存容量、CPU 型号、主机内存、SSD 容量、PCIe 代际和 NUMA 关系都需要作为实验前提显式给出。

软件环境方面，实验系统由 PyTOD 评分实现、FlashANNS 候选召回前端、FAISS-GPU 初步 ANN 接口验证组件、RAPIDS 数据处理与资源管理组件、多 GPU 通信和调度运行时共同组成。FAISS-GPU 主要用于验证候选召回接口、设备侧输入输出路径和候选结果格式，完整 FlashTOD 路径中的大规模候选生成以后续接入的 FlashANNS 为主。为了保证结果可复核，本文固定 Python、PyTorch、PyTOD、FAISS-GPU、CUDA、NCCL 以及操作系统版本；CuPy、cuDF、cuML、RMM 等 GPU 数据处理与资源管理组件的版本也一并记录为统一软件环境快照。

三组实验使用同一套实现，但参照对象不同。真实或半真实数据及 1M 合成桥接数据用于核对筛选候选后保留了多少检测效果。单卡实验沿第三章的规模设置，比较同一设备上的不同执行路径；多 GPU 实验则把压力提高到 100M，分别检查复制索引后的吞吐、必须跨卡归并时的代价，以及共享 I/O 对扩展的限制。

\section{数据集与任务设置}

本章沿用第三章的数据安排，但实验目的已经从建立系统对象转向统一验证系统结论，不同规模数据在这里承担的角色也更明确。真实或半真实金融数据对应全文的现实口径，1M 合成数据承担桥接层，单卡实验沿前述规模链路逐层展开，多 GPU 实验则继续延伸到 100M 样本压力场景。

本章所称真实或半真实金融数据，是指经过公开发布、脱敏、匿名化、采样或特征变换后的金融相关任务数据，与金融机构生产系统中的在线原始流量存在差异。它们适合用于检验异常检测链路在真实业务语境下的可用性；10M、50M、100M 等 AMLSim / IBM AML 合成规模则主要服务于系统压力、吞吐扩展和 I/O 路径验证，相关结论应理解为在本文实验平台和生成口径下的工程趋势。

在有效性验证部分，本文继续使用 IEEE-CIS Fraud Detection、Credit Card Fraud Detection 和 DGraphFin 这三类具有代表性的公开金融数据，分别覆盖结构化支付风控、经典信用卡欺诈以及图金融数据场景。具体数据来源和字段特征已在第三章中给出，这里不再重复展开。

在系统性能与扩展实验部分，本文采用第三章已经介绍过的高保真合成金融交易数据。通过规模分层让不同规模分别承担不同验证任务，其中，1M 数据用于连接真实数据验证与系统实验，使检测效果和端到端实现处于同一实验口径；10M 数据是单卡综合性能与多 GPU 扩展的共同起点；50M 数据主要用于观察规模继续增大后单卡链路与多 GPU 扩展的中间趋势；100M 数据则主要服务于多 GPU 扩展、跨卡归并和共享路径冲突实验。

四类任务各有比较对象。评价候选召回与评分时，以标签核对风险排序，并与全量评分名单对照。单卡任务比较同一条链路改变交接方式前后的吞吐、延迟和利用率。多卡任务还要区分两种情况：索引可复制时，考察增加设备能多接下多少查询；查询必须跨卡或争用 I/O 时，则比较结果归并与通道配置。

有效性实验划分训练集、验证集与测试集，并固定随机种子，使不同路径的 PR-AUC、Recall@$k$ 对应同一批评价样本。性能测量固定索引集和查询集，将查询按批持续送入系统，在这一负载下记录 QPS、延迟分位数和资源利用率。前者要求样本与标签相符，后者要求不同配置面对可比的请求。

\section{评价指标与比较原则}

候选范围缩小后，吞吐可能上升，风险排序也可能改变。比较两条检测路径时须同时保留这两方面的记录。到了单卡交接或多卡扩展实验，仅凭吞吐仍无法判断时间花在评分、主机搬运还是共享 I/O 上，需要结合传输和设备占用情况解释。

检测效果以受试者工作特征曲线下面积（Receiver Operating Characteristic Area Under Curve，ROC-AUC）、PR-AUC 和 Recall@$k$ 对照真实标签。分析前 $k$ 名时，还用 Top-$k$ overlap 与全量评分名单对照，检查哪些对象仍在前列。单卡和多卡都以 QPS、平均延迟及 p95/p99 延迟衡量服务表现。解释这些读数时，GPU 利用率、CPU 占用率和显存使用率反映计算与容量约束，I/O 带宽利用率和 CPU$\leftrightarrow$GPU 传输开销占比反映数据搬运的代价。

金融异常样本通常远少于正常样本。此时 ROC 曲线中的假阳性率会被大量真负例稀释，单独使用 ROC-AUC 可能弱化对少数类识别质量的观察；Precision-Recall 曲线更直接地反映精确率与召回率之间的关系\citep{davis2006prroc,saito2015prauc}。因此，本文把 PR-AUC 作为主要效果指标之一，并与 Recall@$k$、Top-$k$ overlap 共同报告。该选择针对本文类别不平衡和风险样本排序的评价目标，并不表示 PR-AUC 在所有数据分布下都优于 ROC-AUC。

同组比较沿用相同的数据源、向量表示和软硬件环境。比较候选前端时，须先对齐候选预算和评分主干；比较复制、归并或共享 I/O 时，则要保持查询到达方式不变。跨规模数据可以用来观察负载加重后的趋势，但不同规模上的两条记录不能作为一次前端替换实验来解释。

\section{核心结果展示}

以下结果分组阅读。1M 桥接实验把检测效果和吞吐放在一起，是因为候选截断可能同时改变两者。分析单卡和多卡开销时，参照则要换成同一组的执行配置。两组即便报告了相同的 QPS，也未必有相同的 p99。

\subsection{FlashTOD 与端到端比较方案}

第一组结果使用 PyTOD 全量评分作为已有评分方法参考，并设置仅召回内部对照、FAISS-GPU + PyTOD 工程组合基线和 FlashTOD 完整方案。四者分别用于观察全量评分、单独召回、简单 ANN + 评分串接以及完整系统协同的效果和吞吐。

\paragraph{四行结果分别比较什么}
对同一个查询，四个方案交付的结果并不完全相同。全量 PyTOD 在不经过候选筛选的条件下产生风险分数，其前 $k$ 个对象既是可与标签核对的风险名单，也是其他方案计算名单重合度时的参照。仅召回方案到检索输出便停止，表中的效果指标反映检索输出所给排序与标签的关系；它没有产生 PyTOD 精细评分。由此，4580~QPS 描述的是少执行一个阶段的路径，不能作为按同样检测质量完成更多请求的证据。

工程组合与完整方案都把候选送去评分，因此比较这两行比单看仅召回的吞吐更接近系统选型问题。不过，从前者切换到后者同时改变了检索前端与阶段间交接。若风险名单变了，应当先核对两个前端送来的候选是否相同；若名单相近而吞吐差距较大，再沿第四章的阶段耗时检查候选重组和设备传输。仅凭这两行的 PR-AUC 和 QPS，无法把差额进一步分摊给检索算法、设备侧交接以及批次重叠。

全量评分名单与真实标签也要分开。绘图数据中，全量评分的前 $k$ 重合度为 1.000，因为参照名单就是它自身；同一行的 Recall@$k$ 为 0.912。FlashTOD 的两项记录分别为 0.898 和 0.877。前者回答风险名单在多大程度上保留了原评分方法的选择，后者关注标签所指的异常对象。两张名单即便有很高的重合度，也可能共同漏掉某些正例。因而，名单重合可以检验评分范围变化带来的扰动，却不能替代有标签的效果评价。

\section{结果讨论}
\label{sec:result-discussion}

1M 桥接实验中，全量 PyTOD 每秒处理 2700 个查询，PR-AUC 为 0.932。FlashTOD 沿用其评分函数，只把召回的候选送入精细评分：吞吐达到 4280~QPS，比全量评分高约 58.5\%，PR-AUC 则降至 0.906。0.026 的面积差是这组数据上可以量出的效果代价；它没有直接说明在业务选定的告警阈值下会漏掉多少笔异常交易。

把成熟的 ANN 接口接到 PyTOD 前面，是否已经足够？FAISS-GPU + PyTOD 这条工程对照路径得到 3490~QPS、PR-AUC 0.883；完整链路对应 4280~QPS、0.906。两项读数在该任务上都高于简单串接，但这不是 FAISS 与 FlashANNS 的独立检索基准。要辨别前端选出的邻域和阶段间的数据传递各起了多大作用，还得分开看候选内容与执行时间。

检索返回的候选编号和局部距离还不是 PyTOD 的评分输入。在分段链路中，GPU 先把它们传回主机，CPU 按查询重排后再送回 GPU；仅仅缩短检索时间，并不会少走这两趟。FlashTOD 在设备上保留索引映射，按查询组织评分张量，并让外存读取与可执行的计算重叠。端到端比较同时改变了前端和交接方式，不能把两条链路的差额全部归给某一种检索算法。

表~\ref{tab:single-gpu-benefit-source}可以把上述解释核对到相邻配置。只加速召回时，QPS 从 3180 增至 3470，p99 从 67.0 降至 61.5~ms；改用 GPU 侧交接后，两项读数为 3950 和 53.8~ms。到了完整配置，每查询 PCIe 往返已从原始链路的 6.2 次降至 4.2 次，GPU 利用率从 48.5\% 升到 63.5\%，此时达到 4550~QPS 和 45.5~ms 的 p99。候选预算限制送入评分端的邻域规模；同一批候选是否必须先回主机，则由交接方式决定。

为了区分不同优化项，可沿单个请求的关键路径归集耗时。将重叠区间只计入一次，并将等待计给阻塞该请求的阶段，端到端时间可写成
\begin{equation}
  T_{\mathrm{total}} =
  T_{\mathrm{prep}} + T_{\mathrm{retrieve}} + T_{\mathrm{pack}} +
  T_{\mathrm{score}} + T_{\mathrm{merge}} + T_{\mathrm{io}} .
  \label{eq:end-to-end-time-breakdown}
\end{equation}
式~\eqref{eq:end-to-end-time-breakdown}中，$T_{\mathrm{prep}}$表示查询准备时间，$T_{\mathrm{retrieve}}$表示候选召回时间，$T_{\mathrm{pack}}$表示候选组织与张量化时间，$T_{\mathrm{score}}$表示 PyTOD 评分时间，$T_{\mathrm{merge}}$表示多 GPU 归并时间，$T_{\mathrm{io}}$表示外存访问与主机---设备传输。候选预算主要改变 $T_{\mathrm{score}}$的输入规模，设备侧候选组织直接压缩 $T_{\mathrm{pack}}$，异步 I/O 与计算重叠减少 $T_{\mathrm{retrieve}}$ 中的等待，而多 GPU 归并会额外引入 $T_{\mathrm{merge}}$。这个分解与表~\ref{tab:single-gpu-benefit-source}中 PCIe 往返、GPU 利用率和尾延迟的同向变化一致。

多 GPU 结果回答的是另一类问题。索引可复制时，replicated 路径能直接复用单卡闭环，CPU 只需调度请求和汇总小规模结果。容量约束迫使系统分片时，GPU merge 在本文 100M 实验中的平均延迟和 p99 低于 CPU aggregation，但它仍需通信和流协调。多卡共享 PCIe/SSD 路径还会增加 I/O 排队，因此卡数增加并不等于线性扩展。

规模增大后，吞吐、尾延迟和风险排序的变化不能互相代替。以图~\ref{fig:scale-trend}的跨规模记录为例，完整路径从 10M 到 50M 的吞吐由 2440 降到 930~QPS，p99 从 42.2 增至 76.8\,ms，PR-AUC 则由 0.889 降到 0.848。到 100M 时，完整路径仍高于同组初步融合的吞吐（335 对 270~QPS），但其 p99 已达 118.5\,ms。这里可以判断同一规模、同一比较组中选哪条路径更快；能否用于需要特定响应时限的业务，还取决于该时限。跨规模结果中的 335~QPS 与第五章通道绑定实验的 12650~QPS 虽同标为 100M，却不是同一实验组的两个版本，不宜据此计算加速倍数。

有些业务问题不能从曲线面积回答。比如审核人员每批只能看固定数量的告警，关心的是截断位置以上有多少真实异常，以及候选路径漏掉的对象中有多少在全量评分时本可进入名单。PR-AUC 汇总了不同阈值上的表现，不能把 0.026 的面积差直接解释为漏掉某个比例的交易。要回答上述问题，至少得按同一批样本对齐标签、全量分数和候选路径分数，并能区分“没有进入候选”和“评分后落在截断位置以下”。本文未从汇总数据推算这些数量。

这些结论限定在已经比较的路径内。FAISS-GPU + PyTOD 属于本文构造的工程组合基线；它不是对其他外存 ANNS 系统的替代评测。当前数据不支持把效果和吞吐上的取舍外推为 FlashTOD 对 HNSW、IVF/IVF-PQ 或 DiskANN 的普遍优势。

\section{局限性分析}

超大规模实验主要依赖 IBM AML / AMLSim 等高保真合成数据。这类数据可用于施加吞吐、存储路径和多 GPU 扩展压力，却不能完全替代真实金融机构的在线负载、噪声结构和概念漂移。关于 10M、50M 和 100M 规模的结论因而限定为当前平台上的工程趋势。

PyTOD 全量评分的时间和中间结果存储开销限制了它在大规模压测中的覆盖范围。本文在 1M 桥接口径保留全量评分参考，10M 以上主要观察工程组合方案、FlashTOD 与多 GPU 内部路径。这能回答系统扩展问题，但不等同于所有规模下的全量评分横向实验。

现有对比已覆盖技术能力边界、PyTOD 全量评分参考、FAISS-GPU + PyTOD 工程组合基线以及 FlashTOD 内部路径消融。比较范围仍然有限：本文没有在相同候选预算和 PyTOD 评分后端下穷尽 HNSW、IVF/IVF-PQ 与 DiskANN 等可替换前端，也未新增 PyOD CPU 实验。所以，结论不包含对所有 ANNS 方法或异常检测系统的全面优势声称。

这些性能差额只适用于所列硬件、查询集、候选预算和批处理参数。现有汇总值能用来找出值得复核的路径；对于没有完整重复轮次的配置，仅凭汇总值既不能恢复标准差和误差棒，也不能判断再次运行时还会出现多大的差异。

\paragraph{怎样复核一条结果}
以表~\ref{tab:core-summary}中 FlashTOD 的一行为例，核对 0.906 与核对 4280 需要不同的底层记录。前者需取回同一评价集的样本标识、标签和风险分数，按原有方式处理分数并列以及未返回对象，再计算曲线面积。只留下排名靠前的若干交易，无法还原整个评价集上的曲线；用这一个面积值也画不出唯一的精确率---召回率曲线。后者需要知道计时窗口内完成了多少查询以及窗口的实际时长。一个请求若含一批查询，请求数、批次数和查询数便有三个不同的分母。复测时必须先固定计数单位，再比较 QPS。

尾延迟还需要保留分布。假设两个时间窗完成的请求数不同，将两个窗口各自的 p99 取算术平均，通常得不到所有请求合并后的 p99。复核整轮结果时，应有能配对的请求起止时间，或足以按相同规则重算分位数的记录；复核轮与轮之间的波动，则应单独保留各轮的配置、处理数量和时长。这两种重复的单位不同：一个稳定窗口里采到了许多请求，不等于已经完成了多轮独立运行。附录中的文件组织可以容纳这些材料，但现有汇总图并未提供每组的原始分布。因此这里保留离散实测配置点，不补绘误差条，也不插值构造一个未经测试的候选预算。

表~\ref{tab:result-audit-units}把复核所需的观测单位分开列出。同一笔交易可以在压测时被请求多次，在效果评价中却仍然只有一个样本身份；用压测请求的出现次数给标签加权，就会把重复请求较多的交易看得更重。反过来，将性能日志按交易编号去重，也会漏掉真实发生的服务工作。因此，两种记录可以通过配置和样本标识关联，却不能以同一张去重表兼作两个指标的分母。

\paragraph{区分候选预算与数据路径的作用}
若在后续复测中调整候选预算，应先固定查询集、索引和评分函数，再观察每个预算下实际返回了哪些近邻，并在同一评价集上计算效果。预算从小到大时，精细评分面对的样本集合可能改变，不能在横轴只标一个吞吐率就将四个端到端方案连成预算曲线。本文的四个点属于不同方案，尚不能给出满足特定告警召回要求所需的最小预算。

若要单独检验交接开销，则应反过来固定候选：对同一份候选编号、距离和查询映射，分别经过主机重组和设备侧组织，再交由同一评分端。这样能够隔离交接位置，却排除了检索过程中的 I/O 等待，所得差异也就不能直接作为在线服务的加速比。这两类复测需要保留的中间量不同。第四章的递进式实验已经给出了路径组合变化的方向，但现有记录不足以补齐两类独立对照；本文不为未测配置绘制曲线。

\section{本章小结}

1M 桥接任务中，FlashTOD 用较小的候选集换得更高吞吐，仍未达到 PyTOD 全量评分的 PR-AUC。压缩评分范围与加快候选交接的效果也不能混算：前者可能改变风险名单，后者要在同一候选输入上才便于比较。扩大到多卡后，只有当每张卡都能容纳副本时，才可以按查询直接分流；一旦改用分片，结果归并和共享通道上的等待都要计入端到端代价。
