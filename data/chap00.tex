\chapter{绪论}

\section{研究背景与意义}

金融异常检测面对的是具体业务对象。它可能是一笔金额和地域组合异常的交易，也可能是账户在短时间窗内突然改变的行为序列，或由设备指纹、登录地点和交易对手共同构成的高风险模式。在实际检测系统中，检测效果与执行效率共同构成业务约束\citep{aggarwal2017outlier,song2024financialriskstgnn}。吞吐不足会造成请求堆积，尾延迟过高则可能使告警错过处置窗口，高频交易流持续进入系统后，风险告警必须在有限时间内完成。

金融数据的可用监督信息往往滞后于交易本身。欺诈、洗钱等标签需要经过规则命中、人工复核或后续调查才能确认，已确认异常在全量样本中占比很低，业务规则和交易行为变化还会使原有模式逐渐失效\citep{phua2010fraudsurvey,akoglu2015graph}。单笔记录只能提供局部视角；账户历史、时间窗统计和交易关系网络常常需要一同参与判断。这些数据条件使异常检测很难只依赖一次离线训练和固定阈值，也增加了在线特征组织和候选筛查的成本。

图~\ref{fig:fin-ad-business-scene}概括了本文所关注的业务环境。单笔交易特征、账户时间窗统计、设备与地域信息以及关系结构特征需要在进入检测链路前形成一致的输入表达；异常分数和风险排序又要及时返回上层业务。这里不展开金融行业的一般流程，关键约束只有两个：输入持续增长，告警时间预算有限。前者抬高计算与存储压力，后者限制了系统依靠离线批处理消化峰值流量的空间\citep{pei2021gpudatabase,zhang2023gpuolap}。

数据规模较小时，主要开销来自中央处理器（CPU）上的距离计算、排序和聚合耗时。将评分算子迁移到图形处理器（GPU）后，主导瓶颈随之转移。全量距离或近邻计算仍可能产生远大于输入矩阵的中间结果；查询向量和候选结果跨越 CPU--GPU 边界，分别经历主机至设备（H2D）和设备至主机（D2H）的传输；候选编号（ID）、距离与排序信息若在主机侧重新组织，还会增加同步点。索引无法完全驻留显存时，固态硬盘（SSD）访问开始进入关键路径。扩展到多 GPU 后，结果归并还受高速外围组件互连（PCIe）链路、非一致内存访问（NUMA）拓扑及共享输入输出（I/O）带宽的限制。

图~\ref{fig:scale-bottleneck-migration}描述了主导因素随系统规模和执行环境发生的变化。小规模阶段缩短 CPU 算子时间即可得到明显收益；当评分已经 GPU 化，系统开始受数据驻留位置和模块边界影响；当单卡链路被压缩，多 GPU 调度、跨卡归并与共享 SSD 路径才成为新的上限。只优化某个检测器或检索算子，无法保证端到端吞吐同步提高\citep{song2026vectoranns,li2024multigpunuma}。

精细评分不必直接从全量样本开始。近似最近邻（Approximate Nearest Neighbor，ANN）检索先为查询选出一组候选，评分模块只在这个范围内计算异常分数。候选预算由此约束了评分工作量，也限定了参与评分的近邻范围：若漏掉与异常判断有关的邻域，后端无法靠更精细的计算将其补回；若保留过多候选，又难以减轻评分压力。检索与评分之间的数据传输也有独立的开销。即使候选数量已经减少，只要检索结果仍须返回 CPU 打包，评分前就要再做一次 H2D 传输。

本文据此构建两阶段异常检测系统 FlashTOD。系统以张量化异常评分库 PyTOD 对候选集合评分\citep{zhao2022tod}，候选集合由外存近似最近邻搜索（Approximate Nearest Neighbor Search，ANNS）系统 FlashANNS 提供\citep{xiao2025flashanns}。单 GPU 部分研究查询、候选和评分中间张量的设备侧驻留与传递；多 GPU 部分研究查询调度、跨卡结果归并和共享 I/O 竞争。本文讨论的是这些已有能力在金融大规模异常检测链路中的协同组织与优化实现，不将其表述为新的异常检测理论模型，也不把当前实验结果外推为对全部金融风控部署条件的普遍结论。

\subsection{核心系统问题}

上述研究范围内有四个直接影响端到端表现的问题。它们分别落在评分、召回、模块边界和多设备扩展阶段，后文的系统设计与实验验证均围绕这四类问题展开。

\paragraph{异常评分阶段的高复杂度计算问题}

一批输入向量能够装入显存，并不代表能在同一块显存上完成全量评分。距离型和密度型检测需要从距离计算和排序中得到近邻，再据此估计局部密度或聚合邻域信息\citep{aggarwal2017outlier,zhao2022tod}。如果把所有样本两两之间的距离同时保存，单是距离矩阵就要占用 $O(n^2)$ 的存储空间。朴素实现逐维保存成对差分，所需空间还取决于特征维度。因此，评分阶段的计算开销取决于候选预算，显存需求还取决于计算中保留的中间量。

\paragraph{候选召回阶段的存储访问与吞吐瓶颈问题}

索引可驻留显存时，近邻搜索和候选维护主要在设备上完成。索引超出显存后，同一次搜索还可能等待 SSD 读页。此时即便采用相同的 ANN 算法，单次读取的数据量、在途请求数，以及读页与候选距离计算和更新的重叠程度，都会影响吞吐\citep{song2026vectoranns,xiao2025flashanns}。候选预算也不能只按检索耗时设定：缺少评分所需的近邻，异常对象的分数和名次可能改变，使前 $k$ 名结果对已标记异常的召回率（Recall@$k$）下降；若保留更多候选，PyTOD 的距离计算、近邻筛选（\texttt{topk}）和聚合开销又会增加。

\paragraph{CPU--GPU 数据传输与阶段同步问题}

检索结果包含候选编号、距离、局部名次，以及候选编号与原始样本之间的映射。若这些字段返回 CPU，由主机侧的候选重组函数（\texttt{pack\_candidates}）重新打包，执行顺序为：GPU 检索 $\rightarrow$ D2H $\rightarrow$ CPU 候选重组 $\rightarrow$ H2D $\rightarrow$ GPU 评分。一次检索即使足够快，两轮数据搬运、对象转换和同步仍会抬高端到端时延。问题3因此聚焦设备侧候选表达和连续执行，具体定位 CPU--GPU 通信开销出现的位置\citep{pei2021gpudatabase,zhang2023gpuolap}。

\paragraph{多 GPU 扩展中的结果聚合与共享 I/O 瓶颈问题}

索引复制（replicated）使每张 GPU 保留完整索引并独立处理查询，设备间依赖较少，适合吞吐优先且索引可以复制的条件；索引分片（sharded）有利于容量扩展，却需要合并各卡局部结果。无论采用哪种组织方式，多张 GPU 都可能竞争同一 PCIe 交换路径、NUMA 远端内存或 SSD 通道。设备数量增加后，通信、归并和 I/O 排队可能同时增长，吞吐因而不一定与卡数成正比。问题4据此比较不同部署路径的适用条件与扩展代价\citep{li2024multigpunuma,cuvs_multi_gpu_nn}。

\subsection{研究边界与主线}

本工作研发的FlashTOD定位于高效金融风险检测系统协同与执行路径优化研究，沿用 PyTOD 的评分能力，重点研究它与候选召回前端之间的系统接口、数据驻留和执行顺序。FlashANNS 属于已有 ANNS 系统；本文使用其候选检索能力，异步 I/O 机制和索引算法沿用原系统设计。GPU 数据处理工具集（RAPIDS）负责组织中间数据，GPU 向量检索库（FAISS-GPU）用于验证候选接口；页锁定内存支持主机与设备间传输，英伟达集合通信库（NCCL）负责跨卡通信。

当前系统部署环境基于单机单 GPU 与单机多 GPU构建。多机分布式索引、跨机通信和集群调度没有进入本文验证。实验使用公开真实或半真实金融数据检验两阶段链路的可用性，并使用高保真合成数据观察大规模吞吐、时延和扩展趋势；这些输入不能等同于银行生产流量。现有外部基线覆盖也不完备，结论只适用于本文的数据、硬件、候选预算和实现路径。全文的主线因而限定为三部分：FlashTOD 协同框架、单 GPU 数据路径优化和单机多 GPU 扩展。

\section{研究目标与技术路线}

本文的目标是在既定检测方法和硬件条件下，降低候选召回---异常评分链路的系统开销，并检验该链路在单机 GPU 环境中的扩展边界，共同观察检测效果、QPS 和尾延迟。

检索前端和评分后端必须按同一种方式解释输入向量。对表格型交易记录，向量来自缺失值处理、类别编码和时间窗统计；对金融图，向量承载节点属性与邻域统计。同一任务的两个阶段可以共用一份向量，不必为了评分重新提取原始特征。但检索输出是一组近邻编号和距离，后端仍须按查询找到对应的特征，才能构造 PyTOD 的评分张量。

第三章先把金融数据整理为统一向量输入，以 FlashANNS 产生候选集合，再由 PyTOD 完成候选集上的张量化评分，对应问题1和问题2。这个阶段建立功能链路，并通过 PR-AUC、Recall@$k$ 等指标衡量候选预算对检测效果的影响。

候选集合生成后，新的瓶颈出现在模块边界。FlashANNS 输出的候选 ID、局部距离和排序信息需要按查询批次还原与原始样本的对应关系，再组织成 PyTOD 可消费的评分张量。第四章把查询表示、候选 ID、距离、局部排序、索引映射和评分中间张量尽量保持在设备侧，并利用异步 I/O、双缓冲和必要的页锁定内存减少等待。这里对应问题2和问题3。

当单卡链路得到压缩后，多 GPU 扩展才具有实际意义。第五章比较多 GPU 扩展的索引复制主方案、容量受限时的设备侧归并路径以及共享 I/O 约束，对应问题4。索引可复制时，请求由 CPU 控制面分发到不同设备，每张卡沿用单卡的召回---评分闭环；容量迫使索引分片后，局部结果必须跨卡归并，通信和共享存储路径随之进入热路径。第六章在统一实验口径下汇总检测效果、阶段耗时、QPS、p99 延迟和资源利用率。表~\ref{tab:research_route}概括了这条路线的实现层次。

\section{主要工作与技术贡献}

本文完成的工作沿三条主线组织。

\begin{enumerate}
  \item FlashTOD 协同框架。在金融大规模异常检测的统一向量输入上，本文将 FlashANNS 候选检索能力和 PyTOD 张量化评分组织为两阶段执行链路。检索结果经由候选 ID、距离、局部排序和索引映射与评分张量建立对应，使 PyTOD 可以按候选预算执行后续评分。本项工作沿用两个系统原有的检索和评分能力，贡献集中在 FlashTOD 中的链路组织、接口适配与实验验证。
  \item 单 GPU 数据路径优化。针对 GPU 检索后须经 CPU 重组候选、再返回 GPU 评分的折返路径，设计 GPU 主导执行链路，使候选结果和评分中间张量尽量保持在 GPU 侧，并结合异步流水线、双缓冲、页锁定内存及 RAPIDS 数据后端控制必要的边界开销。FAISS-GPU 只用于前期设备/主机指针（device/host pointer）路径和候选接口验证，最终的外存召回主路径由 FlashANNS 承担。
  \item 单机多 GPU 扩展。索引能在每张卡上保留一份时，CPU 控制面按查询分配任务，同一查询的召回和评分留在一张 GPU 上。容量受限、需要汇集各卡局部结果时，本文考察设备侧归并与 NCCL 通信。多个请求还可能争用 PCIe、NUMA 或 SSD 路径，因此多卡实验把查询分发和拓扑感知 I/O 控制分开考察。
\end{enumerate}
