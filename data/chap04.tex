\chapter{多卡并行扩展与归并优化}

\section{多卡扩展需求分析}

第四章已经从单 GPU 视角完成了系统级优化，并初步说明在 GPU 主导端到端执行链路、异步 I/O---计算流水线和后端重构协同作用下，单卡场景中的主要损耗从主机---设备边界转向设备侧检索与评分过程。随着输入规模继续增大、查询并发进一步提升、候选索引逼近单卡显存上限，单卡系统仍会同时遭遇三类上限：计算上限、容量上限和调度上限。

第一类需求来自计算上限。当候选召回和异常评分都已稳定驻留在 GPU 侧时，单卡吞吐最终会受限于单设备的计算资源。此时，即便继续压缩局部路径开销，系统整体 QPS 仍然难以随业务峰值线性提升。第二类需求来自显存与索引容量上限。在更大索引或更大规模合成扩展数据集条件下，单 GPU 可能无法同时容纳完整索引、副本缓存以及评分中间张量，索引规模决定常驻索引的占用，候选预算影响批次工作空间，增加设备数量则改变可用的索引布局\citep{cuvs_multi_gpu_nn,cuvs_multi_gpu_ivf_host}。第三类需求则来自调度压力。金融近实时异常检测同时要求平均吞吐、延迟分位数和资源利用率保持稳定；一旦请求在单设备上集中堆积，即使平均性能尚可，尾延迟也会迅速恶化。

本文在单机内扩展 FlashTOD，关注的是查询分发方式、单卡索引容量和共享路径带宽对吞吐及尾延迟的影响\citep{cuvs_multi_gpu_nn}。进入多卡场景后，局部结果的归并位置、CPU 在关键路径上的参与程度及共享存储路径的拥塞情况共同影响扩展效率。

对吞吐优先的金融近实时检测，本文把查询作为分工单位。各卡均能容纳完整索引时，本文采用索引复制（replicated）：接到查询的卡自行召回和评分，不必为这次查询向其他卡收集候选。若受显存或部署条件限制而必须拆分索引，才需要为同一查询增加设备间通信和跨卡归并。

\section{多卡扩展策略设计原则}

多卡部署可按查询或按索引划分工作负载。不同查询由各卡独立处理时，卡间无需交换候选；同一查询访问多个分片时，归并需等待各分片返回。第四章已经压缩了单卡上从候选召回到评分的数据路径。当单卡容量满足索引复制条件时，各卡沿用这条路径，并行处理不同查询。

一次查询如果拆到多张卡上，即使其中一张卡很早就完成检索，也不能立即返回完整结果。系统还要收齐其他分片的候选，并按同一查询归并。将不同查询分给持有完整索引的设备则没有这个中途会合点：每张卡使用本地候选完成评分，再交回结果。GPU 向量检索库（cuVS）的索引复制模式也按卡分发查询，以提高整机查询吞吐\citep{cuvs_multi_gpu_nn}。

索引复制受单卡显存容量约束。每张卡除了保存索引副本，还同时承载当批候选和评分张量，各卡显存之和并不是单个查询可用的容量。cuVS 区分了偏向吞吐的索引复制（replicated）与偏向容量扩展的分片（sharded）\citep{cuvs_multi_gpu_nn,cuvs_dist_mode}。在 FlashTOD 中，若常驻索引超过单卡可用显存，增加相同的副本不能提高索引容量，扩展需要改变索引布局。

主机侧传递调度状态与传递候选数据对应不同的 CPU 工作负载。按队列负载分配微批时，主机只需知道请求归属和设备状态；若还要在主机上重排各卡返回的候选编号与距离，候选本身便要跨过设备边界。cuVS 文档所列的部分多卡接口要求数据集、查询和输出位于主机内存\citep{cuvs_multi_gpu_ivf_host}。本文将批处理、负载均衡、监控及少量最终结果留给 CPU，不在这一层重新组织评分张量。

分片路径仍要为归并付出代价。将局部结果留在 GPU 上能省去主机聚合，却不能省去卡间交换，也不能让尚未返回的分片提前完成。NVIDIA 集合通信库（NCCL）将通信操作异步提交到指定的 CUDA 流。由分组开始与结束函数（\texttt{ncclGroupStart}、\texttt{ncclGroupEnd}）包围的同一组操作使用多个流时，会引入同步点\citep{nccl_stream_semantics}。这正是本文把设备侧归并留给容量受限配置、而没有在复制路径中也安排一次跨卡归并的原因。

\section{多卡执行架构}

索引复制（replicated）把显存用于保存副本，换得各张卡独立服务不同查询的能力\citep{cuvs_multi_gpu_nn}。在 FlashTOD 中，CPU 将请求组成批次或微批，分发给持有完整索引的 GPU。收到批次的设备就地组织查询向量、检索候选并完成评分，只把最终的小规模结果交给 CPU 汇总。这样可以在不拆开单卡链路的情况下增加整机吞吐，但复制的仍是同一份索引：索引超出单卡容量时，增加副本数不能解除容量限制。

在执行流程上，数据并行与索引复制架构可以形式化表示为：给定总查询集合 $Q=\{q_1,q_2,\ldots,q_m\}$，调度器将其划分为若干子批次 $\{B_1,B_2,\ldots,B_g\}$，并将这些子批次分配给 $g$ 张 GPU。每张 GPU $G_j$ 本地维护一份完整索引 $\mathcal{I}_j=\mathcal{I}$，对其收到的批次 $B_j$ 独立执行
\begin{equation}
  C_j = \mathcal{R}(B_j,\mathcal{I}_j), \qquad S_j = \mathcal{F}(B_j,C_j),
  \label{eq:multi-gpu-local-loop}
\end{equation}
式~\eqref{eq:multi-gpu-local-loop} 中，$\mathcal{R}$ 表示候选召回，$\mathcal{F}$ 表示异常评分。由于每张 GPU 都能本地完成完整闭环，因此系统不需要在查询处理中途引入设备间依赖。

索引复制增加显存占用，但简化了执行路径。各查询相互独立，调度器按请求或微批次将其分配给不同设备；每张 GPU 沿用第四章已经优化好的本地执行链路，不需要为多卡场景重新拆解候选召回与评分接口；系统只需汇总少量最终结果，无需在处理过程中持续维护跨卡依赖。基于这些特点，本文将索引复制定义为多 GPU 扩展的主方案。

\paragraph{复制的容量条件}

索引复制的容量边界由单卡峰值显存占用决定。以表~\ref{tab:hw-config}中的 RTX 3090 为例，四张卡各有 24\,GB 显存。四个副本分别服务四组查询，每个查询的索引和工作空间仍位于本地卡。索引初始化仅占用其中一部分显存；批次执行期间，候选缓冲区、PyTOD 评分张量和运行时工作区与索引同时驻留，构成高于索引静态占用的峰值。

单卡容量约束见式~\eqref{eq:replica-memory-bound}。设 $M_{\mathrm{avail}}$ 为该卡可供服务使用的显存，$M_{\mathrm{res}}$ 为索引及必要常驻数据在设备上的占用，$M_{\mathrm{work}}(t)$ 为批次执行到时刻 $t$ 时额外占用的工作空间。各项按互不重叠的内存区域计量，复制方案要求每张参与计算的卡均满足
\begin{equation}
  M_{\mathrm{res}} + \max_t M_{\mathrm{work}}(t) \leq M_{\mathrm{avail}} .
  \label{eq:replica-memory-bound}
\end{equation}
工作空间按同一时刻实际占用的显存区域计量。同一缓冲区先用于召回、再用于评分时只计一次；前一批评分与后一批召回重叠时，两批同时占用的区域均计入峰值。外存索引中，设备缓存占用显存，尚在 SSD 上的索引页不占用显存。减小微批影响随批大小变化的工作空间，不改变索引等常驻数据的占用；常驻部分已经超出单卡容量时，复制条件对所有批大小均不成立。现有实验报告了给定规模下的部署结果，未记录各区域的逐时显存占用，也未测定 FlashTOD 支持的最大样本数。

\section{CPU 控制面调度与负载均衡}

在索引复制架构下，CPU 承担控制面工作，包括请求队列维护、微批形成、按 GPU 负载分发批次、控制有界批处理策略，以及在各 GPU 完成本地闭环之后接收最终小规模输出。

请求队列组织方面，系统采用统一入口队列接收查询请求，并根据队列长度、GPU 空闲度和微批策略动态形成批次。低时延推理系统和可预测深度学习服务系统的研究都表明，面向吞吐与尾延迟的批处理策略，需要在设备利用率和排队时间之间做持续折中；cuVS 动态批处理文档则为本文的多 GPU 实现提供了更接近工程接口层的参考\citep{crankshaw2017clipper,gu2020clockwork,cuvs_dynamic_batching}。单个微批包含的查询数同时影响设备并行度与组批等待时间。较小的批次包含的并行任务少；在到达速率相同时，更大的目标批次通常需要更长的组批时间。

即使各卡持有相同索引，轮流派发相同数量的请求也不能保证它们同时处理完毕。cuVS 为复制索引提供负载均衡（\texttt{LOAD\_BALANCER}）与轮询（\texttt{ROUND\_ROBIN}）两类搜索模式\citep{cuvs_dist_mode}。本文的调度器按当前负载分配查询。设备正在处理积压请求时，新到微批的排队时间也计入该批次的端到端延迟；第 99 百分位延迟（p99 延迟）反映了这些较慢请求的表现。

请求完成后，CPU 收集异常分数、Top-$k$ 排序结果和必要的日志元信息。局部候选、评分中间张量以及尚待归并的设备侧结构不属于最终输出，无须随结果一起回传。

请求排队与设备执行具有不同的计时边界。复制模式下，查询在派发前经历组批和队列等待，派发后由一张卡独立完成召回与评分。增大目标批大小会增加单次派发的工作量；请求到达稀疏时，较早进入队列的查询还经历等待同批请求的时间。表~\ref{tab:multi-gpu-summary}报告既定负载下的端到端延迟，未单独测量生产流量到达分布或组批等待时限。

分片改变了等待的对象。同一查询在多张卡上分别检索时，先完成的卡只能给出局部结果，只要还有一个必要分片未返回，最终名单便不能确定。平均分配查询数有助于平衡复制模式下的工作量，却不能消除这种单查询内部的等待。请求尚未派发时的等待属于控制面排队；派发后等待最后一个分片返回，属于局部检索阶段；各卡交回局部输出后，归并还包括结果传输和排序。这三段时间都进入端到端延迟，只有第一段发生在派发之前。

\section{跨卡归并场景下的 GPU 侧归并}

当索引超出单卡容量，或同一查询需要访问多卡上的局部索引时，单卡副本无法独立完成检索。系统改用分片索引，每张卡只返回与本分片有关的结果。同一查询的局部结果经设备间传输、流同步和归并后形成最终输出。这部分工作只发生在跨卡检索路径，独立处理不同查询的副本不交换局部候选。因此本文仅在复制路径不适用时使用跨卡归并。

本文的分片路径在 GPU 侧组织与合并局部结果，CPU 接收最终的小规模输出。cuVS 在分片模式下给出了根设备归并（\texttt{MERGE\_ON\_ROOT\_RANK}）与树形归并（\texttt{TREE\_MERGE}）两种方式，为本文设计设备侧归并路径提供了参考\citep{cuvs_dist_mode}。与主机侧聚合路径相比，设备侧归并路径的主要收益在于减少大规模结果回传和主机侧排序开销，使跨卡合并尽可能延续设备侧处理逻辑；额外的通信与同步组织也使其复杂度高于索引复制主方案。

在设备间通信实现方面，本文采用 NCCL 作为主要通信机制，并将通信流与局部计算流明确分离。NCCL 文档指出其通信操作异步入队到指定的 CUDA 流，同组操作涉及多个流时会引入同步点\citep{nccl_stream_semantics}。设备侧归并省去了大批候选经主机重排的步骤，但仍包含设备间传输及其与本地计算之间的同步。该路径与索引复制的开销不同，即使减轻了 CPU 负载，单次查询也仍依赖其余分片的返回时刻。

\paragraph{跨分片局部结果的可比条件}
分片内的首位候选是该分片中与查询距离最近的样本。两个分片的首位候选具有相同的局部名次，仅凭名次无法确定其全局次序。最近邻归并的排序键是同一查询在同一距离定义下的近邻距离；风险结果归并的排序键则是异常分数。局部行号也只有连同分片的样本映射才能还原为原始对象。同一行号分别出现在两张卡上，并不足以判断它们对应同一笔交易。

主机归并和设备归并接收同一批局部结果时，两者的可比性取决于排序键、截断规则和并列项的处理方式。例如，并列分数跨越截断位置时，两份名单中的对象可以不同而分数仍相同。对于依赖近邻密度的评分，各分片局部分数的排序也不同于在完整邻域上重新计算分数。表~\ref{tab:multi-gpu-summary}中的两条归并记录报告了吞吐、延迟和利用率，刻画的是归并位置带来的执行路径差异。实验未报告这两条路径的逐样本分数，分片评分与全量评分的等价性不在本组验证范围内。

\section{拓扑感知 I/O 通道绑定与准入控制}

多张 GPU 各自执行本地检索，并不意味着每张卡也拥有独立的读页通路。如果读请求经过同一条 SSD 通道或 PCIe 链路，排队仍可能压低整机吞吐、抬高 p99 延迟。GPU 直连存储（GDS）通过直接内存访问（Direct Memory Access，DMA）在存储设备和 GPU 显存之间传输数据，省去 CPU 中转缓冲；传输效率仍受硬件拓扑约束\citep{gds_overview}。本文的 I/O 通道（I/O lane）按物理连接组织。运行前识别 GPU 与 SSD 所经的 PCIe 根复合体（PCIe root complex）、交换机（PCIe switch），以及相应的 NUMA 节点；运行时据此尽量将 GPU 绑定到合适的 SSD 通道。准入控制限制每条通道的在途请求（in-flight requests）数，避免请求同时涌入。

\section{多卡扩展实验与结果分析}

单卡性能比较主要使用 10M 和 50M 样本。多卡实验沿用第三章的规模设置，另外在 100M 下检验跨卡归并和共享 I/O 路径。两组实验的对照变量不同：索引复制时比较独立通道与共享路径冲突（shared-path conflict），索引分片时比较设备侧归并与主机侧聚合。各路径的配置见附录 B 表~\ref{tab:multi-gpu-exp-setup}。图~\ref{fig:qps-vs-gpu} 汇总展示索引复制路径的扩展曲线与共享路径下的 p99 延迟变化，图~\ref{fig:latency-quantiles} 展示不同归并路径下的延迟变化，图~\ref{fig:io-lane-impact} 用于比较 I/O 通道配置对扩展性的影响，表~\ref{tab:multi-gpu-summary} 对总体结果进行了汇总。

索引复制方案在 1/2/4 GPU 条件下保持了较为稳定的 QPS 增长和相对平稳的延迟变化，说明在索引可复制的前提下，查询级并行和本地闭环执行更符合本文的吞吐优先目标。与之对应，本地评分 + 设备侧归并和本地评分 + 主机侧聚合的对比用于比较索引分片后的归并位置：两者都建立在索引分片的前提下，但在本文实验口径下，设备侧归并的平均延迟、p99 延迟和 CPU 利用率低于主机侧聚合，说明一旦必须跨卡归并，把局部结果留在设备侧处理更有利于控制路径开销。

共享路径的代价体现在尾延迟上。四卡 100M 配置中，绑定通道时的 p99 为 45.1\,ms，共享路径为 56.6\,ms。两组配置的卡数相同，均不涉及跨卡归并，因此该延迟差反映的是 PCIe/SSD 通道配置的影响。

\paragraph{索引复制的扩展效率}
表~\ref{tab:multi-gpu-summary}的前三行使用 10M 索引复制配置。设 $Q_g$ 是 $g$ 张卡合计完成的每秒查询数，则吞吐扩展倍数为 $Q_g/Q_1$，扩展效率为 $Q_g/(gQ_1)$。以 4550~QPS 为单卡起点，两卡为 $7780/4550\approx1.71$ 倍，效率约为 85.5\%；四卡为 $13620/4550\approx2.99$ 倍，效率约为 74.8\%。这里的效率指实际吞吐占同卡数理想吞吐的比例，与表中的 GPU 利用率口径不同。四卡组的 GPU 利用率高于两卡组，但从两卡增加到四卡时，吞吐增幅低于卡数增幅，扩展效率随之下降。实验未按请求区分排队、共享链路等待与设备执行的耗时，因此这部分扩展损失只有整机层面的测量结果。

\paragraph{100M 配置下的归并与通道对照}
在 100M 压力场景中，配置表~\ref{tab:multi-gpu-exp-setup}提供了区分实验组的依据。归并组固定四卡、索引分片、批大小 3072 和拓扑感知绑定，对照变量为局部评分结果的归并位置。改用设备侧归并时，QPS 从 9580 变为 11380，CPU 利用率由 48.5\% 降到 41.5\%，p99 从 39.0 降至 33.8\,ms。设备侧归并免去了局部结果回传主机的步骤。两组端到端延迟均包含跨卡通信，实验未将通信耗时与主机排序耗时单独计量。

通道组采用完整副本和批大小 4096，没有跨卡归并。两卡绑定相对共享路径的吞吐差为 $7520-6830=690$~QPS，四卡时差额扩大到 $12650-10420=2230$~QPS。在绑定路径上，卡数由二增至四时，p99 仍从 37.2 升至 45.1\,ms。通道绑定减轻了共享路径压力，但增卡后的尾延迟仍高于两卡配置。这一组的吞吐增量伴随慢请求延迟增加。通道组的 12650 与归并组的 11380~QPS 对应不同的索引布局和批大小，二者不构成仅改变归并位置的对照。

\paragraph{平均延迟与尾延迟的部署约束}
多卡配置对平均延迟与尾延迟的影响并不一致。在绑定组中，两卡到四卡的平均延迟由 23.4 降至 22.1\,ms，p99 却由 37.2 升至 45.1\,ms（表~\ref{tab:multi-gpu-summary}）。共享路径组则是两项延迟一起上升。平均延迟反映全部请求的总体水平，p99 刻画较慢请求。绑定组的两个指标变化方向相反，说明平均耗时下降并未伴随尾延迟下降。

GPU 利用率反映测量窗口内的设备使用情况，不能定位单次请求的等待。四卡共享路径上的 GPU 利用率为 56.5\%，改用绑定路径后为 72.2\%。绑定组的设备忙碌比例更高，但该差额以测量窗口为单位，不是单个请求所节省的读页时间。现有统计未将尾部请求与设备利用率采样逐一配对。

端到端耗时跨越主机排队、微批形成、检索读页和结果返回多个环节。分片查询还包含等待各分片完成后的归并。队列驻留时间、存储访问时间和分片完成时刻分别属于不同环节，本组汇总数据未提供以请求标识关联的分段耗时。

\section{本章小结}

四卡在 10M 复制组达到 13620~QPS，处理的仍是同一份索引。增加的资源用于同时服务更多查询，并没有扩大单张卡能容纳的索引。索引分片后，归并位置影响尾延迟：本章四卡分片对照中，设备侧归并的 p99 低于主机侧聚合，但设备间的结果交换依然存在。

尾延迟同样约束部署规模。100M 通道实验里，即使采用绑定，增卡后平均延迟和 p99 也没有朝同一方向变化。在这组配置中，增加卡数提高了整机 QPS，却未降低慢请求的延迟。第六章将这组结果与检测效果对照，分别分析候选评分范围和多卡执行路径的影响。
