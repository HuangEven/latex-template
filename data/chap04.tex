\chapter{多卡并行扩展与归并优化}

\section{多卡扩展需求分析}

第四章已经从单 GPU 视角完成了系统级优化，并初步说明在 GPU 主导端到端执行链路、异步 I/O---计算流水线和后端重构协同作用下，单卡场景中的主要损耗从主机---设备边界转向设备侧检索与评分过程。随着输入规模继续增大、查询并发进一步提升、候选索引逼近单卡显存上限，单卡系统仍会同时遭遇三类上限：计算上限、容量上限和调度上限。

第一类需求来自计算上限。当候选召回和异常评分都已稳定驻留在 GPU 侧时，单卡吞吐最终会受限于单设备的计算资源。此时，即便继续压缩局部路径开销，系统整体 QPS 仍然难以随业务峰值线性提升。第二类需求来自显存与索引容量上限。在更大索引或更大规模合成扩展数据集条件下，单 GPU 可能无法同时容纳完整索引、副本缓存以及评分中间张量，系统必须在缩小索引规模、降低候选预算和增加设备数量之间进行权衡\citep{cuvs_multi_gpu_nn,cuvs_multi_gpu_ivf_host}。第三类需求则来自调度压力。金融近实时异常检测同时要求平均吞吐、延迟分位数和资源利用率保持稳定；一旦请求在单设备上集中堆积，即使平均性能尚可，尾延迟也会迅速恶化。

因此，对本文系统而言，多 GPU 扩展需要在保持检测效果、延迟分位数和实现复杂度可控的前提下兼顾查询分发、索引容量和共享路径的带宽约束\citep{cuvs_multi_gpu_nn}。进入多卡场景后，局部结果的归并位置、CPU 在关键路径上的参与程度及共享存储路径的拥塞情况共同影响扩展效率。

对吞吐优先的金融近实时检测，本文把查询作为分工单位。只要各卡能够保存一份完整索引，就采用索引复制（replicated）：接到查询的卡自行召回和评分，不必为这次查询向其他卡收集候选。若受显存或部署条件限制而必须拆分索引，才需要为同一查询增加设备间通信和跨卡归并。

\section{多卡扩展策略设计原则}

多卡部署可按查询或按索引划分工作负载。不同查询由各卡独立处理时，卡间无需交换候选；同一查询访问多个分片时，归并需等待各分片返回。第四章已经压缩了单卡上从候选召回到评分的数据路径。当单卡容量满足索引复制条件时，各卡沿用这条路径，并行处理不同查询。

一次查询如果拆到多张卡上，即使其中一张卡很早就完成检索，也不能立即返回完整结果。系统还要收齐其他分片的候选，并按同一查询归并。将不同查询分给持有完整索引的设备则没有这个中途会合点：每张卡使用本地候选完成评分，再交回结果。cuVS 的索引复制模式也按卡分发查询，以提高整机查询吞吐\citep{cuvs_multi_gpu_nn}。

决定是否复制时，约束来自单卡，而非各卡显存容量之和。每个副本除了容纳索引，还要留出当批候选和评分张量的空间。cuVS 区分了偏向吞吐的索引复制（replicated）与偏向容量扩展的分片（sharded）\citep{cuvs_multi_gpu_nn,cuvs_dist_mode}。在 FlashTOD 中，若常驻索引超过单卡可用显存，增加相同的副本不能提高索引容量，扩展需要改变索引布局。

主机侧传递调度状态与传递候选数据对应不同的 CPU 工作负载。按队列负载分配微批时，主机只需知道请求归属和设备状态；若还要在主机上重排各卡返回的候选编号与距离，候选本身便要跨过设备边界。cuVS 文档所列的部分多卡接口要求数据集、查询和输出位于主机内存\citep{cuvs_multi_gpu_ivf_host}。本文将批处理、负载均衡、监控及少量最终结果留给 CPU，不在这一层重新组织评分张量。

分片路径仍要为归并付出代价。将局部结果留在 GPU 上能省去主机聚合，却不能省去卡间交换，也不能让尚未返回的分片提前完成。NCCL 通信可以异步进入指定的 CUDA 流；同一 \texttt{ncclGroupStart/End()} 组内使用多个流会引入同步点\citep{nccl_stream_semantics}。这正是本文把设备侧归并留给容量受限配置、而没有在复制路径中也安排一次跨卡归并的原因。

\section{多卡执行架构}

索引复制（replicated）把显存用于保存副本，换得各张卡独立服务不同查询的能力\citep{cuvs_multi_gpu_nn}。在 FlashTOD 中，CPU 将请求组成批次或微批，分发给持有完整索引的 GPU。收到批次的设备就地组织查询向量、检索候选并完成评分，只把最终的小规模结果交给 CPU 汇总。这样可以在不拆开单卡链路的情况下增加整机吞吐，但复制的仍是同一份索引：索引超出单卡容量时，增加副本数不能解除容量限制。

在执行流程上，数据并行与索引复制架构可以形式化表示为：给定总查询集合 $Q=\{q_1,q_2,\ldots,q_m\}$，调度器将其划分为若干子批次 $\{B_1,B_2,\ldots,B_g\}$，并将这些子批次分配给 $g$ 张 GPU。每张 GPU $G_j$ 本地维护一份完整索引 $\mathcal{I}_j=\mathcal{I}$，对其收到的批次 $B_j$ 独立执行
\begin{equation}
  C_j = \mathcal{R}(B_j,\mathcal{I}_j), \qquad S_j = \mathcal{F}(B_j,C_j),
  \label{eq:multi-gpu-local-loop}
\end{equation}
式~\eqref{eq:multi-gpu-local-loop} 中，$\mathcal{R}$ 表示候选召回，$\mathcal{F}$ 表示异常评分。由于每张 GPU 都能本地完成完整闭环，因此系统不需要在查询处理中途引入设备间依赖。

索引复制增加显存占用，但简化了执行路径。各查询相互独立，可按请求或微批次分配给不同设备；每张 GPU 都能沿用第四章已经优化好的本地执行链路，不需要为多卡场景重新拆解候选召回与评分接口；系统只需汇总少量最终结果，无需在处理过程中持续维护跨卡依赖。基于这些特点，本文将索引复制定义为多 GPU 扩展的主方案。

\paragraph{复制的容量条件}

索引复制的容量边界由单卡峰值显存占用决定。以表~\ref{tab:hw-config}中的 RTX 3090 为例，四张卡各有 24\,GB 显存。四个副本服务四组查询，并不意味着任何一个查询都能使用四张卡的显存。即使索引初始化成功，处理一个批次时还要留出候选缓冲区、PyTOD 的评分张量和运行时工作区。若只用索引文件大小与显卡标称容量比较，会低估运行时的显存需求。

可以将这一条件写成式~\eqref{eq:replica-memory-bound}。设 $M_{\mathrm{avail}}$ 为该卡可供服务使用的显存，$M_{\mathrm{res}}$ 为索引及必要常驻数据在设备上的占用，$M_{\mathrm{work}}(t)$ 为批次执行到时刻 $t$ 时额外占用的工作空间。各项按互不重叠的内存区域计量，复制方案要求每张参与计算的卡均满足
\begin{equation}
  M_{\mathrm{res}} + \max_t M_{\mathrm{work}}(t) \leq M_{\mathrm{avail}} .
  \label{eq:replica-memory-bound}
\end{equation}
这里取同一时刻的工作空间总量。召回结束后可复用的缓冲区不应在评分阶段重复计入；若上一批次尚在评分而下一批次已开始召回，两批同时使用的区域则都要计入。外存检索时，SSD 上未驻留的索引页不计入显存，设备缓存仍需计入。这个条件用于解释部署选择，不能据此给出 FlashTOD 的最大样本数；现有实验表没有记录这些区域的逐时占用。若超限部分来自批次工作区，可以先减小微批；若常驻部分本身已经超限，缩小批次就无济于事。

\section{CPU 控制面调度与负载均衡}

在索引复制（replicated）架构下，CPU 的职责需要被严格限定。本节所讨论的控制面工作主要包括请求队列维护、微批形成、按 GPU 负载分发批次、控制有界批处理策略，以及在各 GPU 完成本地闭环之后接收最终小规模输出。

请求队列组织方面，系统采用统一入口队列接收查询请求，并根据队列长度、GPU 空闲度和微批策略动态形成批次。低时延推理系统和可预测深度学习服务系统的研究都表明，面向吞吐与尾延迟的批处理策略，需要在设备利用率和排队时间之间做持续折中；cuVS 动态批处理文档则为本文的多 GPU 实现提供了更接近工程接口层的参考\citep{crankshaw2017clipper,gu2020clockwork,cuvs_dynamic_batching}。本文把微批作为调节吞吐和尾延迟的控制旋钮：批次过小会浪费设备并行能力，批次过大又会推高排队等待。

即使各卡持有相同索引，轮流派发相同数量的请求也不能保证它们同时处理完毕。cuVS 为复制索引提供负载均衡（\texttt{LOAD\_BALANCER}）与轮询（\texttt{ROUND\_ROBIN}）两类搜索模式\citep{cuvs_dist_mode}。本文优先按当前负载动态分配查询，考虑的是排队时间：一张卡前面的请求尚未处理完时，再向它派发微批，可能拉长整机的第 99 百分位延迟（p99 延迟）。

请求完成后，CPU 收集异常分数、Top-$k$ 排序结果和必要的日志元信息。局部候选、评分中间张量以及尚待归并的设备侧结构不属于最终输出，无须随结果一起回传。

从一个请求的经历来看，队列等待与设备执行是两段不同的时间。查询到达后可能先等待同批的其他请求；微批交给一张有完整索引的卡后，查询就不必等待别的卡提供候选。此时把更多请求放入微批，可能提高每次发往设备的有效工作量，却也会延后最早到达的请求。尤其在到达稀疏的时段，同样的批大小对排队时间的影响会不同于持续注入查询的压测。表~\ref{tab:multi-gpu-summary}给出的是既定负载下的端到端延迟，不能从中倒推出一个对生产请求普遍合适的等待时限。

分片改变了等待的对象。同一查询在多张卡上分别检索时，先完成的卡只能给出局部结果，只要还有一个必要分片未返回，最终名单便不能确定。平均分配查询数有助于平衡复制模式下的工作量，却不能消除这种单查询内部的等待。诊断时需要区分请求尚未派发、某张卡尚未交回局部结果，以及各卡已完成但仍在归并三种状态。若将三类等待都计入调度耗时，便无法区分队列分发、局部检索和归并传输的开销。

\section{跨卡归并场景下的 GPU 侧归并}

当索引超出单卡容量，或同一查询需要访问多卡上的局部索引时，单卡副本无法独立完成检索。系统改用分片索引，每张卡只返回与本分片有关的结果。要还原这次查询的输出，还需组织局部结果、在设备间传输并协调执行流，这些都是向不同副本分发查询时无需承担的开销。因此本文仅在复制路径不适用时使用跨卡归并。

在此条件下，本文仍坚持一个约束：局部结果尽量在 GPU 侧组织与合并，CPU 只接收最终极小规模结果。cuVS 在分片模式下给出了 \texttt{MERGE\_ON\_ROOT\_RANK} 与 \texttt{TREE\_MERGE} 两类归并方式，为本文设计设备侧归并路径提供了参考\citep{cuvs_dist_mode}。与主机侧聚合路径相比，设备侧归并路径的主要收益在于减少大规模结果回传和主机侧排序开销，使跨卡合并尽可能延续设备侧处理逻辑；额外的通信与同步组织也使其复杂度高于索引复制主方案。

在设备间通信实现方面，本文采用 NCCL 作为主要通信机制，并将通信流与局部计算流明确分离。NCCL 文档指出其通信操作异步入队到指定 CUDA stream，但在同一 \texttt{ncclGroupStart/End()} 组内混用多个 stream 会形成全局同步点\citep{nccl_stream_semantics}。因此，GPU 侧归并的收益建立在一个前提上：通信必须被控制在必要范围内，并与本地计算流合理解耦。若通信组织不当，兜底方案很容易因同步点过多而侵蚀掉原本希望保留的扩展收益。

\paragraph{跨分片局部结果的可比条件}
分片内的首位候选是该分片中与查询距离最近的样本。两个分片的首位候选具有相同的局部名次，仅凭名次无法确定其全局次序。若合并目标是最近邻，应比较同一查询、同一距离定义下的数值；若合并对象是各卡给出的风险结果，则比较的量已经变成异常分数。局部行号也只有连同分片的样本映射才能还原为原始对象。同一行号分别出现在两张卡上，并不足以判断它们对应同一笔交易。

这一区别也关系到设备侧归并的验证。对给定的一批局部输出，若主机与设备采用同一比较键和截断规则，归并结果应能逐查询核对；有并列分数时，还应检查差异是否只出现在截断位置。这种核对检验的是相同局部输入下两种归并路径的输出一致性。对于依赖近邻密度的评分，把不同分片上已经算出的局部分数排序，并不能自动恢复在完整邻域上重算的分数。表~\ref{tab:multi-gpu-summary}的归并行给出吞吐、延迟和利用率，没有在这一对配置下另报逐样本分数。这组结果可用于比较归并位置的执行开销，不足以证明分片评分与全量评分等价。

\section{拓扑感知 I/O 通道绑定与准入控制}

多张 GPU 各自执行本地检索，并不意味着每张卡也拥有独立的读页通路。如果读请求经过同一条 SSD 通道或 PCIe 链路，排队仍可能压低整机吞吐、抬高 p99 延迟。GDS 可通过直接内存访问（Direct Memory Access，DMA）在存储设备和 GPU 显存之间传输数据，省去 CPU 中转缓冲；传输效率仍受硬件拓扑约束\citep{gds_overview}。本文的 I/O 通道（I/O lane）按物理连接组织。运行前识别 GPU 与 SSD 所经的 PCIe 根复合体（PCIe root complex）、交换机（PCIe switch），以及相应的 NUMA 节点；运行时据此尽量将 GPU 绑定到合适的 SSD 通道。准入控制限制每条通道的在途请求（in-flight requests）数，避免请求同时涌入。

\section{多卡扩展实验与结果分析}

单卡性能比较主要使用 10M 和 50M 样本。多卡实验沿用第三章的规模设置，另外在 100M 下检验跨卡归并和共享 I/O 路径。这里要区分两种对照：索引复制时比较独立通道与共享路径冲突（shared-path conflict），索引分片时比较设备侧归并与主机侧聚合。各路径的配置见附录 B 表~\ref{tab:multi-gpu-exp-setup}。图~\ref{fig:qps-vs-gpu} 汇总展示索引复制路径的扩展曲线与共享路径下的 p99 延迟变化，图~\ref{fig:latency-quantiles} 展示不同归并路径下的延迟变化，图~\ref{fig:io-lane-impact} 用于比较 I/O 通道配置对扩展性的影响，表~\ref{tab:multi-gpu-summary} 对总体结果进行了汇总。

索引复制方案在 1/2/4 GPU 条件下保持了较为稳定的 QPS 增长和相对平稳的延迟变化，说明在索引可复制的前提下，查询级并行和本地闭环执行更符合本文的吞吐优先目标。与之对应，本地评分 + 设备侧归并和本地评分 + 主机侧聚合的对比用于比较索引分片后的归并位置：两者都建立在索引分片的前提下，但在本文实验口径下，设备侧归并的平均延迟、p99 延迟和 CPU 利用率低于主机侧聚合，说明一旦必须跨卡归并，把局部结果留在设备侧处理更有利于控制路径开销。

共享路径的代价体现在尾延迟上。四卡 100M 配置中，绑定通道时的 p99 为 45.1\,ms，共享路径为 56.6\,ms。两组配置的卡数相同，均不涉及跨卡归并，因此该延迟差反映的是 PCIe/SSD 通道配置的影响。

\paragraph{索引复制的扩展效率}
表~\ref{tab:multi-gpu-summary}的前三行使用 10M 索引复制配置。设 $Q_g$ 是 $g$ 张卡合计完成的每秒查询数，则吞吐扩展倍数为 $Q_g/Q_1$，扩展效率为 $Q_g/(gQ_1)$。以 4550~QPS 为单卡起点，两卡为 $7780/4550\approx1.71$ 倍，效率约为 85.5\%；四卡为 $13620/4550\approx2.99$ 倍，效率约为 74.8\%。这里的效率指实际吞吐占同卡数理想吞吐的比例，与表中的 GPU 利用率口径不同。四卡的 GPU 利用率高于两卡，而扩展效率低于两卡，这两项观测可以同时成立。要把未达到线性的部分分配给请求排队、共享链路或设备执行，还需逐请求的等待记录；两条吞吐比本身不能给出这种分解。

\paragraph{100M 配置下的归并与通道对照}
在 100M 压力场景中，配置表~\ref{tab:multi-gpu-exp-setup}提供了区分实验组的依据。归并组固定四卡、索引分片、批大小 3072 和拓扑感知绑定，对照变量为局部评分结果的归并位置。改用设备侧归并时，QPS 从 9580 变为 11380，CPU 利用率由 48.5\% 降到 41.5\%，p99 从 39.0 降至 33.8\,ms。设备侧归并免去了局部结果回传主机的步骤。但没有单独的跨卡通信计时，不能把延迟差额全部解释为节省的主机排序时间。

通道组采用完整副本和批大小 4096，没有跨卡归并。两卡绑定相对共享路径的吞吐差为 $7520-6830=690$~QPS，四卡时差额扩大到 $12650-10420=2230$~QPS。在绑定路径上，卡数由二增至四时，p99 仍从 37.2 升至 45.1\,ms。通道绑定减轻了共享路径压力，但增卡后的尾延迟仍高于两卡配置。对于有响应时限的服务，卡数选择受尾延迟和吞吐的共同约束。通道组的 12650 与归并组的 11380~QPS 对应不同的索引布局和批大小，两者之差不能用于估计归并开销。

\paragraph{平均延迟与尾延迟的部署约束}
多卡配置对平均延迟与尾延迟的影响并不一致。在绑定组中，两卡到四卡的平均延迟由 23.4 降至 22.1\,ms，p99 却由 37.2 升至 45.1\,ms（表~\ref{tab:multi-gpu-summary}）。共享路径组则是两项延迟一起上升。均值与 p99 均为汇总指标，无法据此定位延迟增加的具体请求。告警服务的卡数配置还受吞吐目标和尾延迟上限约束。

GPU 利用率反映测量窗口内的设备使用情况，不能定位单次请求的等待。四卡共享路径上的 GPU 利用率为 56.5\%，改用绑定路径后为 72.2\%。这与设备更少等待输入的解释相符，但利用率是整个窗口的统计量，不能把两者之差直接算作节省的 I/O 时间。现有统计未将 p99 对应的请求与利用率最低的采样时段逐一配对。

请求耗时可包括设备执行前的主机排队、组批等待和检索期间的读页等待。分片查询还须等待所有必要分片返回后才能完成归并。区分上述环节的开销，需要按请求标识关联队列、存储访问和分片返回的时间记录。

\section{本章小结}

四卡在 10M 复制组达到 13620~QPS，处理的仍是同一份索引。增加的资源用于同时服务更多查询，并没有扩大单张卡能容纳的索引。索引分片后，归并位置影响尾延迟：本章四卡分片对照中，设备侧归并的 p99 低于主机侧聚合，但设备间的结果交换依然存在。

尾延迟同样约束部署规模。100M 通道实验里，即使采用绑定，增卡后平均延迟和 p99 也没有朝同一方向变化。对于有时限的告警请求，仅凭整机 QPS 无法选定卡数。第六章将这组结果与检测效果对照，分别分析候选评分范围和多卡执行路径的影响。
