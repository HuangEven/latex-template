\chapter{单卡场景下的系统设计与数据路径优化}

\section{单卡系统需求与总体架构}

第三章建立了候选召回与异常评分的两阶段链路。本章在不改变评分方法的前提下，比较不同单卡执行路径的吞吐率和延迟。单卡实验将 CPU$\leftrightarrow$GPU 数据交换、候选组织、I/O 等待与算子同步限定在同一设备路径内，便于区分各阶段的开销。该路径也是后续多卡索引复制实验中每张卡执行本地查询的基础。

单卡显存同时承载一批查询、检索返回的候选以及 PyTOD 评分所需的中间张量。检索结束后，候选缓冲区与评分工作区的占用仍有重叠，因此只按查询向量估算的显存需求低于整条链路的需求。本文在同一张 GPU 上保留查询特征和中间候选，减少主机侧重组引起的往返。索引驻留外存时，GPU 在读页期间处理已就绪的数据。

基于这一目标，本文将单卡系统划分为五个核心模块：数据接入与预处理模块、查询向量组织模块、候选召回模块、异常评分模块以及结果输出与日志模块。它们分别承担原始金融记录接入与字段规范化、统一设备侧查询表示构造、候选集合高吞吐返回、候选集上的张量化评分以及最终结果回传与运行时记录等职责。这样的模块划分把热路径和边界路径区分开来：前四个模块构成候选召回到异常评分的核心执行链路，最后一个模块只在必要边界与主机交互。在原始分段路径上，CPU 先预处理查询，再接收 GPU 检索结果、重组候选并回传 GPU 评分。优化路径将中间候选的交接保留在设备侧。

ANNS 前端生成候选集合，PyTOD 对候选样本进行精细评分。两个阶段通过设备侧的候选表示交接。前期采用 FAISS-GPU 验证候选接口与设备指针路径，完整实现采用 FlashANNS 进行候选检索。单卡优化集中于候选输出到评分输入的转换，以及页锁定内存、异步流和双缓冲的配合。

\section{单卡场景下的瓶颈分析}

原始链路由 CPU 分段组织：查询特征多在 CPU 侧整理，GPU 生成的候选返回 CPU 重组，随后再传回 GPU 评分。检索和评分各自在设备上执行，但两者之间的主机往返引入了额外传输与同步等待。

主机与设备之间的频繁边界交换会削弱候选召回和异常评分的单点加速收益。前期验证的 GPU 索引接受主机指针和设备指针。输入与索引位于同一张 GPU 时无需跨设备拷贝；输入位于主机或另一张 GPU 时，则涉及 CPU$\rightarrow$GPU 或跨设备拷贝，结果也会在完成后返回相应位置。这意味着，如果查询特征在 CPU 侧完成拼接和标准化，再逐批传输到 GPU，那么即便 GPU 检索本身很快，整条链路仍要持续承担入口传输成本。若候选结果又在 GPU 侧生成后回到 CPU 被重新整理，再送入 PyTOD 评分，则一次查询实际上会跨越两轮主机---设备边界。每个查询跨越这些边界都会引入传输与同步，高并发时多个查询还会争用同一条主机与设备间的通路。

候选结果的存放形式影响评分前的重组开销。检索返回候选 ID 时，还可能附有局部距离、索引位置或局部排序。若按查询把这些字段拆成 Python 对象列表，或先写入 pandas 数据帧或主机侧稀疏结构，PyTOD 就不能沿用检索时的设备缓冲。评分启动前，后端要重新按批次排列候选，为它们在 GPU 上构造张量。主机与设备之间的拷贝次数不包含这部分重组开销。

当候选召回需要访问外存或已经存在明显 I/O 压力时，固态硬盘读写 与 GPU 计算之间的串行等待会把前两类问题进一步放大。传统外存驻留（out-of-core）ANN 系统的主要问题之一在于 SSD 访问与 GPU 计算无法有效重叠，距离计算须等待读页完成，从而使高性能 GPU 长时间等待 I/O 完成。而在本文的 FlashTOD 链路中，如果检索内部已经开始重叠 I/O 与计算，但候选召回结束后仍要回到 CPU 完成数据组织和评分前准备，那么被检索阶段隐藏掉的一部分等待会在后续边界重新出现。检索内的读页重叠与检索后的候选回传位于不同阶段，单独加速前端并不改变后者的传输路径。

单卡上还有一部分开销来自临时显存的分配与释放。FAISS 的标准 GPU 资源管理类（\texttt{StandardGpuResources}）预留临时工作区，减少运行期间调用显存分配和释放函数（\texttt{cudaMalloc} 和 \texttt{cudaFree}）引起的同步。页锁定主机内存用于主机与设备之间的数据交换，设备内存池则复用临时显存。即使候选已驻留 GPU，评分启动前反复申请工作区仍会引入资源管理开销。

查询上传和候选回传占用的是主机与设备之间的通路，候选重组占用的则是检索结束到评分启动之间的时间。两者在记录上未必同步变化：即使每批仍然搬运相同次数，若候选在主机上要逐个拆包、重新分组，评分也会推迟。另两类等待发生在设备一侧。读页尚未完成，检索就缺少下一步所需的数据；临时缓冲区的申请若触发同步，已有数据的批次也可能无法继续。实验记录的候选组织耗时和 PCIe 往返次数分别反映阶段交接时间和主机交互频次。GPU 利用率统计整个窗口内设备的忙碌程度，并不标识哪一项依赖阻塞了后续阶段。

\section{端到端评分计算执行链路设计}

针对上一节所分析的瓶颈，本文设计面向单卡场景的 GPU 主导端到端执行链路。这一路径的核心做法是：在接入已有外存 ANNS 前端的基础上，把查询特征组织、候选检索结果传递与异常评分中间张量计算尽量收拢到 GPU 一侧，仅在必要边界通过页锁定内存等机制完成主机交互，从而同时压缩 SSD-I/O 与 GPU 计算之间的串行等待，以及主机---设备边界上的额外搬运。

从总体原则上看，GPU 主导端到端执行链路包含三层含义：查询特征的最终组织尽可能在 GPU 侧完成；候选召回结果以设备侧可直接消费的形式交给异常评分模块；评分阶段产生的中间张量继续在设备侧推进，只有最终分数、排序结果或必要日志信息再回传 CPU。与分段执行相比，检索与评分之间不再经主机交接候选。

\subsection{查询特征在 GPU 侧的驻留与组织}

在原始实现中，金融交易数据通常先以表格形式在 CPU 侧完成清洗、归一化和拼接，再整体打包为查询向量传入 GPU。这样组织虽然直观，但会让所有查询都在入口处承担一次完整的 H2D 成本。本文在这一位置的设计决策，是把部分预处理与特征组织前移到 GPU 数据处理后端，使关键查询向量尽可能在设备侧形成最终表示。RAPIDS 的 GPU 数据帧组件 cuDF，以及与其协同的 GPU 数组计算库 CuPy，提供了批量列运算、张量表达和统计聚合能力，使这一做法在工程上具备可行性\citep{rapids_cudf_pandas}。设备侧完成拼接的查询向量直接传入检索接口，省去了以整批主机缓冲区为中转的步骤。

\subsection{候选检索结果在 GPU 侧的保持与传递}

PyTOD 需要按查询对齐的候选张量。系统尽量让候选 ID、局部距离和索引信息常驻设备（device-resident），直接在 GPU 上把它们组织成评分输入。前期验证选用 FAISS-GPU：输入、输出与索引在同一张 GPU 上时无需额外拷贝；GPU 资源管理接口（\texttt{GpuResources}）支持预分配临时工作区，减少中间缓冲区的申请\citep{faiss_gpu_wiki}。验证时核对的是候选 ID 和距离能否交给 PyTOD；在完整 FlashTOD 路径上，产生这些字段的前端换为 FlashANNS。设备侧保留这份表示，目的是省去评分前的主机打包及相应的阶段等待。

\subsection{异常评分中间张量的 GPU 常驻执行}

PyTOD 评分阶段本身具备张量化执行基础，因此在本文设计中，其主要中间表示包括候选距离矩阵、局部排序结果、聚合统计量和最终异常分数。这些中间张量在 GPU 上连续推进，得到最终小规模输出后再按需回传主机。对象中途离开 GPU 会增加 D2H 成本，并破坏 PyTOD 在设备侧连续执行和批量算子复用的优势。保持设备驻留能够同时减少传输并保留评分阶段的局部性和算子复用。

\subsection{必要条件下的主机侧交互与页锁定内存机制}

GPU 主导执行仍保留必要的 CPU 交互。原始输入读取、部分日志写回、结果落盘以及特定部署场景下的主机接口都需要主机参与。本文把这些交互限制在必要边界，并通过页锁定内存等机制控制相应开销。RMM 的页锁定主机内存资源类（\texttt{PinnedHostMemoryResource}）提供页锁定缓冲区，用于主机与设备之间的数据传输\citep{rapids_rmm_pinned}。这类机制用于降低必要交互对整条热路径的干扰。

因此，单卡热路径只保留必要的主机边界：查询向量、规范化特征、候选 编号、局部距离、局部排序 以及 PyTOD 的距离矩阵、排序和聚合张量尽量在 GPU 侧连续传递；原始数据在主机侧读入，最终异常分数和运行日志按需回传 CPU。这样既保留系统可观察性，也避免候选到评分之间重新形成主机侧折返。

\section{候选召回前端的数据路径组织}

FlashTOD 沿用 FlashANNS 的索引结构、搜索算法和异步 I/O 机制，将其用作外存候选召回前端。单卡接入的关键在于检索完成后的数据交接：PyTOD 依赖按查询组织的候选张量，而前端输出近邻编号、距离和局部排序。

这一路径包含三处接口：查询向量以设备侧对象传入 ANNS 前端；候选编号、距离和局部排序在设备上组织为评分输入；外存读取与 GPU 局部计算按数据就绪顺序衔接。若检索后仍须经 CPU 打包和重组，评分启动前的等待将抵消部分检索加速收益。

\subsection{外存 ANNS 前端的流水线接入}

让 GPU 更直接地访问存储，是降低外存路径主机参与的一类系统思路。GPU 文件系统（GPUfs）为设备线程提供文件访问接口，使设备侧内核能够发起文件访问\citep{silberstein2013gpufs}；GPU 发起存储访问的系统（BaM）则把 GPU、NVMe SSD 与批量访问管理结合起来，减少 CPU 对数据访问关键路径的干预\citep{qureshi2023bam}。这些工作说明，外存吞吐不仅由检索算法决定，访问发起位置、请求聚合和 I/O 与计算的重叠同样重要。本文并未实现 GPUfs 或 BaM，也未将其作为 FlashTOD 的直接依赖；这里借鉴的是减少主机中转、让存储访问与设备计算并行推进的路径组织原则。

索引超出显存时，一次查询所需的节点或向量块可能还在 SSD 上。如果每读一块都要等待读取结束才开始计算，读页等待就会占用检索时间。FlashANNS 采用依赖放松异步流水线（dependency-relaxed asynchronous pipeline），使外存 I/O 与 GPU 上已具备条件的计算重叠\citep{xiao2025flashanns}。FlashTOD 沿用这一检索机制，接入时要处理的是候选到达之后与评分模块的交接。

以一次尚未读完全部图节点的查询为例，GPU 对已到达的向量块计算距离、更新候选，同时 SSD 继续读取其余块。若检索结果仍由 CPU 重组，PyTOD 必须等待候选回传至 GPU 后才能开始评分。FlashTOD 在设备侧完成评分前的候选准备，把前端产出的结果直接交给后端；这一处理针对的是两个模块之间的等待，其计时边界不同于检索内部的读页重叠。

\subsection{GPU 数据处理与候选组织}

检索前端输出按查询分组的候选编号和距离，评分端接收设备张量。这两个阶段之间的表格处理和临时空间分配构成了后端重构的对象。本文在原始 PyTorch/CPU 数据路径基础上引入 RAPIDS GPU 数据处理生态，对金融数据预处理、特征拼接、中间结果组织和批量统计环节进行后端重构\citep{rapids_cudf_pandas,rapids_rmm_pinned}。RAPIDS 在这里用于支撑候选召回前端与评分模块之间的设备侧数据组织，不参与异常评分逻辑。

在字段仍按列存放时，系统尽量用 RAPIDS/cuDF 筛选字段、转换类型并完成窗口统计。随后，候选的拼接和聚合在 设备侧数据帧 或 CuPy 张量上进行。如果在这一步先转成 Python 对象，再为 PyTOD 构造张量，前端省下的搬运便会在接口处重新出现。因此，召回和评分优先通过连续的设备缓冲区交接；设备临时空间由 RMM 内存池管理，必须经过主机的交换则使用页锁定主机端（pinned host）缓冲\citep{rapids_rmm_pinned}。

RAPIDS 在本文中用于稳定热路径的数据和内存后端，后端重构的直接目标，是减少查询准备（\texttt{query\_prep}）、候选打包（\texttt{pack\_candidates}）和检索资源初始化过程中的对象转换与临时分配，使候选召回前端返回的结果能够更低成本地进入 PyTOD 评分阶段。

\subsection{ANNS 检索接口验证与完整路径接入}

本文将候选召回前端定义为连接统一向量输入和 PyTOD 候选评分输入的接口层，具体实现可以接入相应的 ANNS 系统。在实现演进中，本文首先利用 FAISS-GPU 提供的近邻检索接口 完成候选召回链路的初步验证。该阶段主要用于确认 GPU 侧查询输入、候选 ID 与距离输出、设备指针路径和 PyTOD 候选评分接口之间的衔接关系。

完整链路接入 FlashANNS 后，索引可以超过显存，但 PyTOD 对候选输入的要求并未改变。查询向量以设备侧对象进入检索前端；检索返回的编号和距离要保持与查询的对应关系，才能整理为 GPU 上的评分张量。前期用 FAISS-GPU 核对的正是这两个接口。在资源管理上，FAISS 的资源管理接口 与系统侧缓冲区的配合，为检查设备指针传递、临时空间申请及相应的延迟抖动提供了参照\citep{faiss_gpu_wiki}。完整路径沿用这类接口约束，不以 FAISS-GPU 承担外存检索。

\section{单卡执行链路的工程增强}

候选驻留在 GPU 上后，相邻批次仍共享设备资源。单卡路径将异步 CUDA 流与微批双缓冲结合，并复用临时空间以减少显存分配和碎片。运行日志和性能采样用于定位高负载下发生等待的阶段。

查询准备、检索、评分以及必要的主机交互分配到不同的 CUDA 流。前一微批仍在评分时，下一微批使用独立缓冲区组织输入。消费某一张量的算子依赖该张量的写入完成，不依赖其他微批的全部操作完成。中间张量由内存池管理，已用完的区域可供后续批次复用，减少反复申请不同大小的显存所带来的开销。为区分各阶段开销，日志同时记录查询规模、候选数、各阶段耗时、GPU 利用率及 主机与设备 交互次数。

\paragraph{跨批次缓冲区的复用条件}
检索完成只表示前端已写入候选编号和距离。评分端仍需按编号读取样本向量，此时覆盖候选缓冲区会破坏查询与候选的对应关系。即使两个批次的张量形状和类型相同，维度检查也不能发现这类错位。双缓冲允许后一批在独立区域准备输入；前一批使用的区域须等最后一次读取完成后才可覆盖，无须为切换批次而等待整张卡上的任务结束。

缓冲区的生命周期取决于最后一次访问。仅供检索读取的查询向量，其最后一次访问发生在检索阶段；同时作为评分输入的向量，其生命周期延续至评分端读完为止。候选编号在构造评分输入时仍然有效，异常分数则保留至输出排序完成。异步调用的主机函数返回不代表设备操作已经结束。每次交接都同步整张卡，会阻塞无关任务；按缓冲区的读写依赖确定复用时刻，将等待限制在使用同一区域的操作之间。

设备驻留消除了主机侧打包，但没有消除候选组织本身的开销。检索前端按近邻次序写入编号，评分端按查询收集样本向量，两者的访问顺序不同。内存池减少了临时分配，按编号取数和排列张量仍占用设备时间。候选组织耗时与主机往返次数分别反映这两类开销，单凭 GPU 利用率无法将其区分。

\section{单卡实验与性能分析}

为了验证前述单卡系统设计与数据路径优化的有效性，本文沿用第三章定义的单卡规模链路组织实验。其中，真实或半真实数据主要用于确认链路可运行和检测效果不失真，1M、10M、50M 三个合成规模主要用于性能、吞吐和压力分析；二者不直接比较绝对吞吐。1M 承担由真实集过渡到系统实验的桥接角色，10M 与 50M 对应单卡性能分析的主体规模。在这一框架下，本节重点比较四类方案：原始分段执行链路、仅启用候选召回加速的链路、启用 GPU 主导执行链路但不做后端重构的链路，以及本文完整的单卡优化方案。这样的对比口径能够区分不同收益来源：候选召回本身带来的收益、执行链路重构带来的收益，以及后端与工程增强叠加后的整体收益。换言之，这四类方案构成递进式消融实验，用于观察候选召回、数据路径压缩和后端重构在端到端性能中的累积贡献。实验关注的指标包括每秒查询数（Queries Per Second，QPS）、平均延迟与第 99 百分位延迟（p99 延迟）、CPU$\leftrightarrow$GPU 传输次数与体积、GPU 利用率、I/O 利用率以及各阶段耗时分解。

仅加速召回时，前端可以较早返回候选，但评分仍要等 CPU 把候选编号和距离重新组织好。将这一步移到 GPU 之后，检索结果可以直接用于构造评分张量，省去中间结果回到主机再传回设备的过程。外存读取可与已就绪的计算重叠。往返次数记录每次查询的主机交互频次，GPU 利用率记录整个观测窗口内的忙碌程度。两者均不直接计量异步读取与设备计算的重叠时间。

图~\ref{fig:single-stage-breakdown}使用查询准备、候选检索、候选组织、PyTOD 评分和输出五个阶段。1M 原始链路中耗时最长的是候选组织（11.80\,ms），超过检索本身（9.90\,ms）。只加速召回后，候选组织仍需 10.95\,ms；改由 GPU 交接后降至 8.95\,ms，完整路径上为 7.05\,ms。此时检索为 7.95\,ms，已经超过候选组织。以原始路径为参照，完整路径的最大阶段耗时降幅出现在候选组织，而非前端检索。

\section{本章小结}

单卡优化改变了候选从检索出口到评分入口的数据路径。原始链路先在主机上重组候选；设备侧交接则把编号、距离和所属查询一并保留在 GPU 上，后端据此组织 PyTOD 的评分张量。RAPIDS 用于处理这些中间数据，FAISS-GPU 用于前期接口核对，完整链路的检索仍由 FlashANNS 完成。实验分别记录了交接频次和组织耗时：每查询的 PCIe 往返次数反映主机交互频率，候选组织的阶段耗时则包含按编号取数和整理张量的工作。前者按次计量，后者按时间计量；两者都下降，并不意味着每一次往返都有固定的耗时代价。

在 10M 分解中，完整路径仍把 15.10\,ms 用在候选组织上，与检索的 15.30\,ms 接近。两段时间说明设备侧交接省掉了主机往返，却没有省掉按编号取数和构造评分输入。当单卡显存足以容纳索引时，各卡可分别处理不同查询；当索引容量先达到单卡显存上限时，扩展还涉及索引划分与结果归并。下一章分别讨论这两种约束。
