\chapter{全文总结与展望}

\section{全文总结}

金融交易的候选检索和异常评分有两个不同的终点：检索返回近邻，评分需要为待检对象给出风险分数。FlashTOD 保留已有评分模型，把全量评分改为候选集上的评分。对近实时检测，关键在于候选筛选后能保留多少排序信息，以及留下的候选要经过哪些传输和重组才能送入评分端。

在系统架构层面，论文以 PyTOD 为异常评分模块、以 FlashANNS 为候选召回前端，构建了 FlashTOD。这样组织的目的，是把候选召回和异常评分纳入同一条执行链路，使系统能够先在大规模样本中缩小评分范围，再在候选集合上执行张量化异常评分，从而缓解全量评分带来的时间与空间压力。

围绕这一执行链路，论文进一步完成了数据准备与任务建模工作。针对金融交易数据、账户行为数据和图金融数据的差异，本文对输入形式、向量化表示、候选召回目标和异常评分目标进行了统一建模，并形成了按规模逐层推进的数据组织方案。借助这一方案，全文把真实有效性验证、桥接实验、单卡性能口径和多 GPU 压力场景纳入同一实验框架。

单卡实现中，FlashANNS 返回的候选编号和距离留在 GPU，系统按查询与原始样本的映射构造 PyTOD 评分输入。RAPIDS 后端承接中间张量和缓冲区；只有必须与主机交换的数据才走主机传输路径，页锁定内存可用于这些传输。多卡实验从这条单卡路径出发。在 10M 索引复制组，各卡各自处理一批查询，两卡和四卡的吞吐分别达到单卡的 1.71 倍和 2.99 倍。得到扩展的是同时处理不同查询的能力，一份索引仍需能装进单卡。一旦改用分片，各卡只有局部结果，系统需要组织这些结果，经 NCCL 传递后再在设备侧归并。归并与 I/O 等待也不宜混为一谈：在不跨卡归并的 100M 四卡通道对照中，仅把绑定通道换成共享路径，p99 就由 45.1 增至 56.6\,ms。这部分差异不应归因于评分模型或归并算法。

本文前期利用 FAISS-GPU 较完善的 ANN API 完成候选召回接口和 PyTOD 评分衔接验证，并在完整 FlashTOD 路径中以 FlashANNS 作为主要候选召回前端。该处理使 FAISS-GPU 的作用限定在工程验证和接口参照层面，避免将其与 FlashANNS 在大规模外存 ANNS 路径中的职责混同。

综合实验部分则把前述系统设计放回统一验证框架中。在本文设定的数据规模、硬件平台和候选预算条件下，结果显示 FlashTOD 在真实数据口径和 1M 合成桥接口径上能够保持合理的检测效果；在更大规模的高保真合成数据上，单卡优化的主要收益来自候选召回到异常评分之间的数据路径压缩，而多 GPU 数据并行与索引复制方案表现出一定的吞吐扩展能力。随着规模继续增大，I/O 路径与拓扑关系对扩展上限的影响也变得更加明显。

第二章比较已有技术能提供什么能力；效果与吞吐的判断则来自第六章同组的端到端记录。1M 桥接任务中，PyTOD 全量评分的 PR-AUC 为 0.932，吞吐为 2700~QPS；FlashTOD 的对应读数是 0.906 和 4280~QPS。缩小评分范围换来了吞吐，也损失了一部分检测效果。如果问题是“加一个 ANN 前端是否就已足够”，参照对象应换成 FAISS-GPU + PyTOD 的工程组合。它与完整系统之间既更换了检索前端，又改变了候选交接方式，差额不能全算在某个检索算法上。要解释计算、搬运或归并分别起了什么作用，还得看各自的路径对照。

综合来看，本文的主要研究结论与技术贡献可以归纳为三点：
\begin{enumerate}
  \item FlashTOD 将高吞吐候选召回与异常评分组织到同一执行链路中，使系统从全量高复杂度评分转向候选缩减后的精排评分路径，并在本文实验口径下取得更稳妥的效果与效率平衡。
  \item 对同一条单 GPU 链路，缩短候选交接可以在不改变 PyTOD 评分函数的条件下改善吞吐和尾延迟。原始路径先把候选送回主机重组，完整路径直接在设备侧交给评分端。第四章的 10M 阶段分解中，候选组织耗时从 23.90 降至 15.10\,ms，节约的时间来自评分开始之前。这一对照没有拆开缓冲区复用、数据驻留和异步执行的作用，不能据此为每种机制各分配一份收益。
  \item 多 GPU 场景中，数据并行与索引复制可作为吞吐优先条件下的主扩展方案；当索引无法复制时，GPU 侧归并相比 CPU 聚合更有利于减少主机侧路径开销，而扩展收益能否真正保留下来，还取决于存储拓扑与 I/O 路径组织方式。
\end{enumerate}

\section{未来工作展望}

本文的工作主要集中在单机环境下金融大规模异常检测系统的实现与优化。沿着这一主线继续向前推进，仍有若干方向值得进一步深入。这些方向来自本文已经触及但尚未展开的研究边界。

当前的端到端对照回答了两个问题：与 PyTOD 全量评分相比，候选筛选牺牲了多少检测效果；与 FAISS-GPU + PyTOD 简单串接相比，完整路径的吞吐和效果有何不同。内部路径对照还检查了候选组织、数据搬运及多 GPU 归并的开销。要区分不同前端自身的影响，后续可以固定数据、查询集、候选预算和 PyTOD 后端，分别接入 HNSW、PQ/IVF-PQ、DiskANN 或 SPANN\citep{malkov2020hnsw,jegou2011pq,subramanya2019diskann,chen2021spann}，参照 ANN-Benchmarks 的评价方法记录召回率、预算、QPS、尾延迟及资源占用\citep{aumuller2020annbenchmarks}。这项比较应保留同一查询在各个前端返回的候选名单：如果最终风险排序变了，先查近邻集合是否已经不同；若集合相近而耗时相差较多，再核对取数与交接路径。本文未开展这些替换实验，现有结果不能给这些检索路径排出优劣。

\subsection{面向更真实金融场景的数据验证}

本文已经在真实或半真实数据上验证了方法可用性，也借助高保真合成数据完成了大规模系统实验，但更接近生产环境的金融业务数据仍然有限。在严格遵守隐私与合规要求的前提下，后续若能接入更复杂分布、更强业务噪声和更明显概念漂移条件下的数据，将有助于进一步检验 FlashTOD 在真实业务约束下的稳定性，也能更准确地评估系统结论向生产场景外推的边界。

\subsection{面向多机场景的分布式扩展}

本文重点解决的是单机多 GPU 条件下的系统路径组织，多机场景中的跨节点通信、远程结果归并和分布式索引管理尚未进入论文范围。如果继续沿用控制面与数据平面分离的思路，把它扩展到多节点环境，就有机会进一步回答更大规模集群中的查询分发、跨节点索引一致性以及层次化归并问题，这将决定本文方案能否从单机扩展走向更大规模部署。

\subsection{面向更深层存储路径的优化}

本文已经讨论了外存驻留路径、拓扑感知 I/O 控制和 GDS 相关约束，但对更深层的存储访问优化仍然展开得不够。后续可以在现有单机链路之外评估 GPUDirect RDMA，使远端设备或存储数据在满足拓扑和驱动约束时减少主机内存中转\citep{nvidia2026gpudirectrdma}；也可参考 BaM 对 GPU 发起访问、请求批处理和 NVMe 路径的组织方式\citep{qureshi2023bam}，进一步分析查询调度与存储访问的联动。当前实现没有部署 RDMA，也没有集成 BaM。这些技术能否在 FlashTOD 中保留收益，仍需结合网络、SSD、PCIe/NUMA 拓扑和尾延迟进行独立验证。

\subsection{面向图异常检测与时序异常检测的统一扩展}

现有接口只接收定长向量。图金融任务可以把节点属性和邻域统计送进这条路径，但交易关系本身并未在评分时参与逐层计算。若要直接利用图结构，可参考比特币反洗钱图模型和 CARE-GNN 对交易关系、异质邻居与噪声连接的处理\citep{weber2019bitcoinaml,dou2020caregnn}；实体关系随时间变化时，图偏差网络对多变量时间序列的建模可作为另一种参照\citep{deng2021gdn}。引入这些模型后，训练、采样、特征更新和在线推理都需要重新计量，当前向量输入下的吞吐不能直接沿用。

\subsection{面向国产 GPU 平台的验证与部署}

现有实验使用 NVIDIA GPU。迁移到国产 GPU 时，可以先用同一批查询核对近邻编号、距离和评分，再检查向量检索与评分算子之间能否直接交换设备侧数据。即使单卡输出一致，多卡归并所需的通信和外存访问仍依赖目标平台的接口。本文没有这一平台的测量结果，不能从现有吞吐和延迟推定移植后的表现。
